# Preparing data for reproduction

Run commands from the module directory after installing the dependencies in the
[README](../README.md). Data are downloaded or supplied separately and remain
under the gitignored `data/` directory. Rendering uses those local files offline.

## What each example needs

| Example | Data preparation | Reproduction boundary |
|---|---|---|
| Minimal PNG/GIF example | Download WMO; forecast values are generated by the included synthetic fixture | Does not require ETOPO or project radar samples |
| Terrain preparation | Download the exact NOAA ETOPO file below; reuse WMO | Produces a native regional NetCDF and two terrain previews |
| CMA radar mock + terrain | Prepare WMO/ETOPO, use the team's existing CMA NPZs and the bundled REF colour table | Internal development; team members already have the mock samples |

Reproducing the plotting workflow with synthetic input is different from
reproducing the same radar scene. The latter requires the same input samples.

## WMO basemap

The retrieval script requires `curl` and network access:

```bash
.venv/bin/python scripts/acquire_wmo_basemap.py --output data/cache/basemap/wmo
```

The script obtains the official service metadata, styles and vector tiles and
writes cache checksums. Source details and use terms are recorded in
[the WMO source record](../basemap_sources/wmo-source.json). The service may change
or be unavailable; do not silently treat different downloaded content as the
historical sample. Keep the acquisition records with each run. A matching existing
cache can be reused without downloading again.

Then run the synthetic example from the README. It produces its own forecast-like
values locally and labels them as synthetic, not a real forecast.

## ETOPO terrain

Use **ETOPO 2022 v1, 30 arc-second, surface, NetCDF**. This is not a 30-metre DEM.
The [NOAA product page](https://www.ncei.noaa.gov/products/etopo-global-relief-model)
provides official downloads. The exact filename, URL, size, CRS and attribution
are recorded in [etopo2022-source.json](../basemap_sources/etopo2022-source.json).
The global download is approximately 1.64 GB; allow additional disk space for the
regional crop and generated figures.

```bash
mkdir -p data/cache/terrain/etopo2022
curl --fail --location --retry 3 --continue-at - \
  --output data/cache/terrain/etopo2022/ETOPO_2022_v1_30s_N90W180_surface.nc \
  'https://www.ngdc.noaa.gov/thredds/fileServer/global/ETOPO2022/30s/30s_surface_elev_netcdf/ETOPO_2022_v1_30s_N90W180_surface.nc'
```

Compare size and SHA-256 with the recorded source before using it:

```bash
.venv/bin/python - <<'CHECK'
import hashlib, json
from pathlib import Path
record = json.loads(Path('basemap_sources/etopo2022-acquisition.json').read_text())
path = Path(record['local_path'])
assert path.stat().st_size == record['verification']['size_bytes']
with path.open('rb') as stream:
    digest = hashlib.file_digest(stream, 'sha256').hexdigest()
assert digest == record['verification']['sha256'], 'ETOPO differs from the recorded source'
print('ETOPO size and SHA-256 match')
CHECK
```

The expected checksum is our recorded acquisition checksum, not a publisher-signed
checksum. If it differs, investigate the source/version; do not replace the expected
value just to make the check pass. To additionally decode and inspect the full grid:

```bash
.venv/bin/python scripts/verify_etopo.py \
  data/cache/terrain/etopo2022/ETOPO_2022_v1_30s_N90W180_surface.nc \
  --report output/terrain/source-verification.json
```

Create the region used by the current CMA mock example. The explicit extent avoids
depending on any previous local preview output:

```bash
.venv/bin/python scripts/preview_etopo.py \
  --bbox 72.995 134.995 12.205 54.205
```

This creates `data/cache/terrain/etopo2022/cma-domain.nc` and
`output/terrain/cma-domain/manifest.json`, plus two preview PNGs. The crop is checked
against native source values without regridding. Its file contains a creation time,
so each run can have a different byte checksum. Use the **newly generated manifest**
as `--crop-record`, rather than the historical `etopo2022-cma-preview.json`.

## Current CMA radar mock example

Team members already have the mock CMA CREF NPZ sequence. Use its local directory
with `--input`; no new sample download or distribution step is needed for this
internal handoff. The [REF colour table](../resources/cma_ref_colormap.json) is
included with the code as a plotting resource. Its numeric levels and colours are
unchanged from the existing project colour table.

The command below assumes the existing NPZs are at `data/cma-npz/`; replace this
path with their actual location. Keep the bundled `--color-file` argument when
using this source delivery; the existing CLI's legacy default path is unchanged.

```bash
.venv/bin/python -m nib_visualization.cli cma-mock \
  --input data/cma-npz \
  --color-file resources/cma_ref_colormap.json \
  --terrain data/cache/terrain/etopo2022/cma-domain.nc \
  --crop-record output/terrain/cma-domain/manifest.json \
  --output output/cma-mock
.venv/bin/python -m nib_visualization.cli gallery \
  --manifest output/cma-mock/manifest.json
```

This produces `map.png`, `animation.gif`, `manifest.json` and `index.html`. It replays
observations as mock forecast leads and records the actual input file hashes.
To recreate the historical 50-frame scene, use all 50 matching observation NPZs
and the same colour table. Different valid NPZ sequences produce different scenes.

A fresh download and a complete 50-frame radar run were not performed for this
source-package preparation. Public service access and receiving-platform setup
remain environment checks; local generation does not imply browser G4 acceptance.
